# Auto2dLabel v0.6 里程碑定义

> v0.6 = **对话式 Agent 统一入口**：`chat "<指令>"` 成为唯一入口，LLM 与用户多轮对话确定全部参数 → 执行。
> 立项 2026-08-28（用户决策：架构迭代优先——chat 唯一入口 + 智能对话确定参数；auto3dlabel v0.3 的 P1-P4 相应顺延）。

## 背景与决策

现状两入口：`run`（Agent Loop，每图 LLM tool-use 循环）+ `chat`（Planner 单轮 JSON 解析 → 纯代码执行，缺参靠代码级 `ask_with_timeout` 追问）。用户目标：**只接受 `chat "..."` 即可输出**，参数通过 LLM 驱动对话确定（而非固定规则追问）。

技术判断（2026-08-28 论证）：
- **对话式参数确定：值得做**——Planner 从「单轮 JSON 解析 + 代码级追问」升级为「LLM 驱动多轮对话收集」，TaskPlan schema 不变、execute_plan 零改动，成本上限可控
- **多 agent 编排框架（LangGraph/AutoGen/CrewAI 等）：不引入**——本项目 LLM 决策点仅 3 处（规划/质量处置/调参）且条件触发；质量防线在 F4 代码层 + HITL，比 agent 间辩论更可靠更便宜；多 agent 放大唯一外部依赖（DeepSeek）失败面，违背「无 key 零影响」红线

三项锁定决策：
1. **范围**：`parse_dialog` 多轮对话 + `--no-wait` 降级保留 + 通用对话骨架 2D/3D 共用 + 远期 run 并入 chat
2. **形态**：对话循环通用化（auto2dlabel/agent/dialog.py），2D/3D planner 各自提供 prompt + schema（复用不复制）
3. **run 保留**（v0.6 阶段）：Agent Loop 是「LLM 在环处置」唯一形态（evaluate_quality 条件暴露），chat 检测步暂不升级为 Agent Loop；**远期目标**：chat `--agentic` 开关吸收 run，run 命令降级为别名

## Phase 1：对话式 Planner（parse_dialog）✅

### 设计：多轮对话收集

```
chat "检测视频里穿红衣服的人并跟踪"          （无 --no-wait）
  → 第 1 轮：LLM 解析 → JSON + questions[]
     {
       "steps": [{"task_type":"tracking","source":"","prompts":["person"],...}],
       "confirm_timeout": 30,
       "questions": [
         {"id": "step1.source", "question": "视频/图像目录在哪里？"},
         {"id": "step1.prompts", "question": "要跟踪哪些类别？(如 person, car)"}
       ]
     }
  → 代码层一次渲染全部问题（复用 ask_with_timeout 超时交互，自由文本回答）
  → 回喂用户回答 → 第 2 轮 LLM 更新 TaskPlan
  → questions 为空 → 确认 → execute_plan（零改动）
```

### 关键机制

- **JSON schema 扩展**：`questions: [{id, question}]`——id 定位到 `step{id}.{field}`，代码只校验字段存在性，**参数提取仍由 LLM 完成**（自由文本回答喂回 LLM）
- **轮次上限 = 3**（对齐 Agent Loop `max_iterations=3` 红线）；耗尽后走代码兜底补缺（现状 `ask_missing_params` 保留）
- **降级链**：LLM 响应非法 / questions 解析失败 / 无 key → 现有单轮 `parse` + 代码兜底，零行为回退
- **`--no-wait`（timeout=0）**：跳过对话轮，直接代码兜底（现状行为不变）
- **成本**：每轮 1 次 LLM 调用，最多 3 轮；`temperature=0`；prompt 注入 GPU 上下文与模型目录（沿用现有 `_gpu_context_line` + `format_catalog_summary`）
- **通用骨架**：`agent/dialog.py` 提供 `parse_with_dialog(llm, system_prompt, parse_fn, ask_fn, max_rounds=3)`——渲染问题/收集回答/回喂/轮次控制与 schema 无关；2D/3D 各自注入（复用不复制红线）

### 验收

| 项 | 验收 |
| --- | --- |
| 对话闭环 | `chat "检测视频里穿红衣服的人并跟踪"`（无 --no-wait）→ 对话问出 source/prompts → 执行 → 输出 |
| 完整指令零对话 | `chat "检测 /data/images 中的汽车" --no-wait` → 无 questions → 直接执行（行为与 v0.5 一致） |

| 无 key 零影响 | 无 API key → 走代码兜底全默认参数 |
| 3D 贯通 | auto3dlabel chat 同机制（见 auto3dlabel v0.3 P1） |

## Phase 3：mmdet / mmpose 质量与速度引擎（2026-08-30 追加）✅

> 背景：mmlab 全家桶已装（mmdet 3.3.0 / mmpose 1.3.2 / mmtrack 1.0.0rc1），盘点结论——**只挑 2 个算法**做质量/速度档，不做全量接入。

### 盘点结论（单一事实源）

| 库 | 现状 | 决策 |
| --- | --- | --- |
| mmdet 3.3.0 | 仅 cityscapes 权重转换（torchvision 结构推理），运行时零依赖 | **挑 2 个算法接入**（下方） |
| mmpose 1.3.2 | 零使用（姿态走 YOLO-pose） | **RTMPose 精度档**（P3b） |
| mmtrack 1.0.0rc1 | 零使用（跟踪自研 ByteTrack/BoT-SORT 已验证） | **永久排除**——官方停止维护（1.0.0rc1 末版），内建 DeepSORT 质量低于自研 BoT-SORT+CLIP ReID，换引擎引入口径不一致 |
| mmcv / mmengine | 间接依赖 | 无直接产品价值，不立项 |

### P3a：mmdet 双引擎

- **Mask2Former**（实例分割质量档）：COCO 预训练权重现成；与 SAM2（coco_seg 实测 0.6368）同口径出 benchmark——SAM2 mask 易粘连（小目标/密集场景分割红线）时提供质量替代
- **RTMDet**（高召回档）：替换/补充 Faster R-CNN（torchvision）——更快且精度不降
- 接入形态：复用 cityscapes 转换先例（`convert_mmdet_cityscapes_maskrcnn`）或 mmdet 运行时推理封装（detect 协议），以落地验证为准
- **P3a 验收**：Mask2Former vs SAM2 同口径分割 benchmark 出表；RTMDet vs Faster R-CNN 检测 benchmark 出表（精度 + 速度双列）

### P3b：mmpose RTMPose 姿态精度档

- 前置：**先建姿态评测基准**（当前 YOLO-pose 无评测口径）——COCO 17 点 keypoints 评测协议
- 接入 RTMPose-l 精度档，对比 YOLO-pose：小目标/密集人群姿态（YOLO-pose 已知弱点）
- 复用 `models/pose.py` 抽象层（Protocol + Fake 注入，单测零权重铁律）
- **P3b 验收**：姿态基准出表（YOLO-pose vs RTMPose，含小目标/密集场景分层）；精度档生效

## Phase 4：LLM Harness 工程（Token 降本）（2026-08-30 追加）✅

> 背景：LLM 调用点 7 处（planner.parse / parse_with_dialog / _reparse_confirm_edit / Agent Loop ≤3 次每图 / llm_tune_strategy / _llm_plan_once / planner3d 复用）。**「省钱量化」地基缺失：`response.usage` 全丢弃**——先建台账，再谈优化，全部改造以台账前后对比验证。

### 子项（harness 层，不动产品功能语义）

1. **usage 台账**（地基）：LLMClient 统一收集 `{调用点, 时间, prompt_tokens, completion_tokens, cached_tokens(DeepSeek), 模型, 折算费用}` → JSONL 日志；`auto2dlabel cost-report` 命令按调用点聚合（调用数 / tokens / 费用 / 缓存命中率）
2. **max_tokens 分级**：OpenAI 路径缺失（Anthropic 有 4096）——planner 1024 / Agent Loop 2048，防输出失控（Summarize 长文）
3. **json mode**：planner / planner3d / 重解析 / track 等全部 JSON 输出调用点加 `response_format={"type":"json_object"}`——输出更短更稳 + 防 parse 失败重试（隐性双倍费用）
4. **system prompt 前缀稳定化 + messages 规整化**：动态内容（GPU 上下文等）后置，保 DeepSeek 前缀缓存命中；assistant 回传 tool_calls.arguments 规整化后再入 state（LLM 原样写回冗余 JSON 占消息大头）
5. **LLM Evaluate 代码级降级**：质量不达标图（quality.ok == False）触发 LLM 处置决策时——失败/超时降级为确定性规则（0 框 → 降阈值等，规则与 `pick_alternate_model` 同源），不中断整图流程；可配开关直接走规则（Agentic 特性保留为默认）

### 验证

- 改造前后同一指令集跑台账对比：调用次数 / prompt+completion+cached tokens / 折算费用（DeepSeek 单价）→ 数字落 `tests/test-v0.6.md`
- 缓存命中率（cached_tokens / prompt_tokens）进报告

### P4 验收

| 项 | 验收 |
| --- | --- |
| 台账 | 每次 LLM 调用落 JSONL（含调用点/usage/费用）；`cost-report` 命令输出聚合表 |
| max_tokens | OpenAI 路径全部调用点有上限；超限不静默截断（日志可见） |
| json mode | 全部 JSON 输出调用点生效；parse 失败率不升 |
| 前缀缓存 | 同指令二次调用 cached_tokens 命中（报告可见）；messages 规整化无行为回归 |
| Evaluate 降级 | mock LLM 失败 → 代码级处置完成，流程不中断；开关生效 |

## 远期（v0.6 后，不承诺）

- chat `--agentic`：检测步可选升级为 Agent Loop（吸收 run 的 LLM 在环处置能力）；run 命令降级为 `chat --agentic` 别名
- 多 agent 研究决策模式：一次性多视角评审（同一问题 2-3 个独立 LLM 调用投票，用完即弃）——留给研究型任务（如 LabelAny3D 复现结论）
