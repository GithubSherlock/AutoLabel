# Auto2dLabel v1.1 里程碑定义

> v1.1 = **RAG 与多 Agent 演进**：标注经验沉淀为可检索知识（P1 RAG 最小闭环）+ 质检升级为独立 Critic Agent（P2 跨模型交叉校验）。
> 立项 2026-09-16（设计定案）→ **P1 + P2 交付 2026-09-17**（逐 Phase 质量门全绿）。设计论证全文见 `docs/AutoLabel_plan.md` §RAG 与多 Agent 演进调研。

## 背景与决策

v1.0（Agentic 交互化，P1–P5 ✅ 2026-09-06）完成后，交互外壳与可见性已就位，但两处能力仍是「一次性」的：**① 标注经验不沉淀**——每次规划都从零开始，历史会话里「哪个域用哪个模型/阈值、踩过什么坑」的结论没有回流到 LLM 上下文；**② 质量评估是自我确认**——LLM Evaluate 与 planner 同 provider/同模型，容易复现同一偏见。

v1.1 两项交付分别对应这两处，**红线约束**（四条，贯穿全 Phase）：
1. **纯本地零新外部 API** — 向量库与 Embedding 均本地权重
2. **LLM 调用点不扩容** — 质检仅 `quality.ok == False` 条件触发（与既有 LLM Evaluate 同一判据）
3. **复用不复制** — 复用 `agent/dialog.py` 骨架、Harness usage 台账、`create_client` provider 注册表
4. **不引入多 agent 编排框架** — 沿用 v0.6 论证（LLM 决策点少且条件触发，质量防线在代码层 + HITL）

三项锁定决策：
1. **RAG 选型下沉** — 文档定案的 `bge-small-zh-v1.5 + FAISS` 改为**复用已集成 ClipModel + numpy 暴力余弦**：零新权重（`weights/hf` 已缓存）、中文实测可用、种子量小无需 ANN 索引
2. **Critic 只出意见不执行** — 独立 prompt + 独立 provider 的第二次 LLM 调用，产出 `{judgment, reason, action}` 建议，**管道不据此重试**（交叉校验是增强不是必需；执行权仍在既有 EvaluateTool）
3. **Router Agent 缓行** — `route_domain` 代码级规则已覆盖（17/17 手动 + 23 用例），**无规则误路由实证前不做**（避免 LLM 分类扩容调用点 + 新失败面）

## Phase 1：标注经验库（RAG 最小闭环）✅

### 设计：零 LLM 入库 + metadata 过滤检索 + planner few-shot 注入

```
标注会话结束（_finalize_step）
  → build_entry 纯代码构造摘要（零 LLM：指令/域/数据集/任务/选型阈值/质量判定/人工修正）
  → append_entry 异步 daemon 线程落 logs/experience.jsonl（去重，不阻塞关键路径）

下次规划（planner.parse / parse_dialog）
  → retrieve(instruction)：metadata 精确过滤（domain/dataset/task_type 非空即参与）
    → CLIP 文本向量 + numpy 暴力余弦 top-k（k=3）
  → format_fewshot 渲染 → 注入 planner.md 的 $experience_fewshot 段
  → 检索失败/空库 → 注入空串（静默降级，RAG 是增强不是必需）
```

### 关键机制

- **检索单元**：`ExperienceEntry`（`agent/experience.py`，frozen dataclass）——`instruction`（检索文本）/ `domain` / `dataset` / `task_type` / `model` / `confidence_threshold` / `quality` / `human_action` / `notes`
- **人工修正零新增采集**：`human_action` 从既有 `*_reviewed.json` 的 `edited_by_human` / `issues` 提取——现有数据回路直接复用
- **embedding 复用**：`_clip_text_embed` 走已集成 ClipModel（`weights/hf` 缓存，零新权重）；transformers 5.x 取 `pooler_output`（与 `get_image_features` 同坑）
- **检索降级链**：`embed_fn` 不可用（无权重）→ metadata 过滤后按原序截断 top-k，**不排序也不报错**
- **种子库**：`configs/experience_seeds.jsonl` 3 条手工结论（cityscapes 小目标需域内权重 / DOTA 航拍失效 + 批量铁律 / 跟踪器选择与 ReID 约束）——冷启动即有 few-shot 可用；运行日志优先于种子
- **注入点单一**：`planner._build_system_prompt(instruction)` 每次解析动态构建；import 期常量 `_PLANNER_SYSTEM_PROMPT` 保留无 few-shot 基础版（8 个测试直接 import 常量断言子串的契约不变）
- **入库挂点**：`cli_execute._finalize_step` → `_record_experience_async`（daemon 线程，入库失败零影响）

### 验收

| 项 | 验收 |
| --- | --- |
| 零 LLM 入库 | `build_entry` 纯代码构造，无 LLM 调用（用例断言） |
| 去重 | 同 `(instruction, model)` 键重复入库返回 False 不追加 |
| 检索正确性 | metadata 过滤优先于向量；过滤后空集 → `[]`；`embed_fn` 缺失 → 原序截断 |
| 注入生效 | planner prompt 含 few-shot 段；检索失败 → 回退基础 prompt（不抛异常） |
| 对比基准 | `experience_benchmark.py` 注入组 vs 基线组（同源 GT/检测器/评估协议），注册 `run_benchmarks.sh experience` 组 |

## Phase 2：质检 Agent 独立化（Critic）✅

- **与 LLM Evaluate 的区别**（`agent/critic.py` docstring 单一事实源）：EvaluateTool 是 **agent loop 内的动作选择工具**（LLM 在 loop 里选 action，`forward` 只执行代码动作、不调 LLM）；Critic 是**独立的一次 LLM 调用**——独立 prompt（`prompts/critic.md`，与 planner 不同源）+ 独立 provider/client + 独立 call_site `evaluate_critic`
- **触发口径**：`quality.ok == False`（`should_criticize`，与 LLM Evaluate 同一判据）；无 key / 失败 / 非法 JSON → **静默跳过**，绝不阻断标注关键路径
- **独立 provider**：`build_critic_client()` 经 `create_client` 走 provider 注册表（台账按 provider+model 记账）；env `AUTOLABEL_CRITIC_PROVIDER` 覆盖（默认 deepseek，用户可配更强模型）——跨模型交叉校验，降低同模型自我确认偏差
- **输出契约**：`{judgment: pass|fail, reason, action}`——`action` 限定在既有四动作白名单（accept / flag_for_review / retry_lower_threshold / retry_swap_model），**只出建议不执行**；结果仅打印 + 记 `steps_results[-1]["critic"]`
- **成本口径**：`auto2dlabel cost-critic` 子命令——`aggregate_usage` 过滤 `evaluate_critic` vs `planner.dialog`/`planner` 两调用点同表对比（复用台账单一事实源，无新聚合逻辑）

### 验收

| 项 | 验收 |
| --- | --- |
| 触发正确 | `ok == False` 才触发；`ok == True` / `None` 不触发 |
| 降级零影响 | 无 key → 跳过；LLM 失败 / 非法 JSON → 跳过（流程不中断） |
| 输出白名单 | judgment / action 非法值 → ValueError（调用方静默跳过） |
| 台账分离 | 独立 call_site `evaluate_critic`；cost-critic 同表对比两调用点 |
| prompt 独立 | `critic.md` 与 planner prompt 不同源（跨模型交叉校验前提） |

## 如实记录

- **Benchmark 数字无差异（预期内）**：`experience_benchmark.py` 已交付并跑通（COCO 3/10/50 图、yolo26x/yolo11n、cityscapes、dota 多组），**注入组与基线组 mAP 逐组相同**（如 COCO 50 图 yolo11n 两组均 0.2891、cityscapes 两组均 0.5228）——唯一差异是 LLM 调用数 +1 次（注入组多一次 planner 调用）。**解读**：few-shot 注入影响的是**规划参数选择**（模型/阈值/批次），而 benchmark 固定了检测器与 conf，规划差异无法体现在 mAP 上；要量化 RAG 收益需「不固定模型/阈值、由 planner 自由选择」的评测协议——**留待后续**（不粉饰为「无收益」）。
- **dota 组两组 mAP 均 0.0**：数据集域边界（COCO 预训练模型在航拍域失效，v0.3 已定性），非 RAG 引入。
- **P1 检索规模**：运行日志实测仅 1 条（`logs/experience.jsonl`）+ 种子 3 条——种子量小，numpy 暴力检索与 FAISS 无性能差异（选型依据之一）。
- **Router Agent 缓行**：见决策 3；`route_domain` 保持单一事实源不变。
