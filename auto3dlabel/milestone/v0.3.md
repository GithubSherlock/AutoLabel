# Auto3dLabel v0.3 里程碑定义

> v0.3 = **对话式 Agent 统一入口（P1，最高优先）** + 精度升级双数据集（P2）+ 相机-LiDAR 融合（P3）+ Web 真 3D 复核（P4）+ 无 LiDAR 域验证（P5）。
> 立项 2026-08-28（用户决策：四方向全上 / three.js 真 3D / BEVFusion KITTI+nuScenes / LabelAny3D 验证先行）；**2026-08-28 追加决策：对话式 planner 提前为 P1，原 P1-P4 顺延为 P2-P5**（auto2dlabel v0.6 对话式 Agent 同周期，3D 侧复用通用骨架）。**2026-08-28 评审修订**（4 处修正 + P4 拆分 + 2 处补充，见各 Phase）。

## 背景与决策

v0.2 完成 mmdet3d PointPillars 接入（KITTI 全 val moderate 82.0 超 zoo）、Tracker3D、nuScenes Mini 支持。v0.3 优先推进对话式 Agent 统一入口（与 auto2dlabel v0.6 双线同构），再沿价值栈推进精度/融合/HITL 体验/无 LiDAR 域。

五项锁定决策（2026-08-28 AskUserQuestion + 追加 + 评审）：
1. **范围**：四方向全上（原 P1 精度 → P2 融合 → P3 Web 3D → P4 LabelAny3D 验证）
2. **Web 形态**：three.js 真 3D 交互（单文件本地化入 static/，不破无构建链红线）
3. **BEVFusion 范围**：KITTI + nuScenes 都要（落地时以权重可用性为准，见 P3 事实修正）
4. **LabelAny3D**：验证先行（前置侦察 + 复现，预算 2-3 天），达标再接入第三引擎
5. **追加（2026-08-28）**：对话式 planner 提前为 P1（架构迭代优先，多 agent 框架不引入——论证见 auto2dlabel v0.6 背景）

**事实核查（2026-08-28，sparse-checkout configs 实证）**：
- mmdet3d v1.4.0 **无 KITTI centerpoint**（centerpoint/ 仅 nus-3d 系列，metafile 无 kitti 条目）→ KITTI 精度升级改走 **PV-RCNN**（`pv_rcnn_8xb2-80e_kitti-3d-3class.py` 现成，zoo car moderate 81.4）；centerpoint 只做 nuScenes 侧
- **BEVFusion 不在 sparse-checkout**（configs 列表无 bevfusion/）→ P3 需补 sparse-checkout + 权重；官方权重仅 nuScenes，**KITTI 无官方融合权重** → KITTI 侧降级方案见 P3
- `download_detector3d.sh` 已含 centerpoint_nus 条目（v0.2 埋钩子），P2/P3 直接扩展

## Phase 1：对话式 Planner（3D 侧接入）✅

- **前置条件（评审修正）**：auto2dlabel v0.6 `agent/dialog.py` 骨架**接口冻结先行**——`parse_with_dialog(llm, system_prompt, parse_fn, ask_fn, max_rounds=3)` 签名为 3D P1 开工前提（双线并行节奏：2D 骨架落盘 → 3D 接入）
- **复用通用骨架**：渲染问题/收集回答/回喂/轮次控制与 schema 无关——复用不复制红线
- **3D 侧注入**：`planner3d.py` 扩展 `TaskPlanner3D.parse_dialog`——Plan3D JSON 加 `questions: [{id, question}]`（id 定位 `frame_id/prompts/det_model/seg_model` 等字段）；对话问出 frame_id / prompts / 引擎选择（2D 反投影 vs LiDAR 直检 pointpillars/pvrcnn/centerpoint——语义已在现有 prompt 映射）
- **降级链**：响应非法 / questions 解析失败 / 无 key → 现有单轮 `parse`（代码兜底默认值），零行为回退
- **`--no-wait`**：跳过对话，代码兜底（现状不变）
- **成本**：每轮 1 次 LLM 调用，≤3 轮；`temperature=0`
- **P1 验收**：`auto3dlabel chat "标注 KITTI 帧 000123 中的汽车和行人"`（无 --no-wait 且缺参）→ 对话问出缺失参数 → 执行；完整指令零对话；mock LLM 回归测试（对话闭环 / 轮次耗尽 / 非法降级）

## Phase 2：精度升级双数据集 + 难类收尾 ✅

- **KITTI**：接入 PV-RCNN（v1.4.0 现成 config，zoo 权重）→ 双引擎路由加 `-d pvrcnn_kitti`；**先 20 帧冒烟再全量**（沿用 v0.2 节奏；全 val 3769 帧预计推理 20-30 分钟 + 官方口径评测 ~95 分钟——耗时预算如实记录）；全 val 官方口径对比表 vs PointPillars（moderate 82.0 基线）
- **nuScenes**：接入 CenterPoint（`centerpoint_pillar02_second_secfpn_circlenms`，权重条目已就绪）→ 简化评测对比 pointpillars_nus（mAP 17.7 基线）
- **难类收尾**：v0.2 记录 Cyclist 全 0、bicycle/motorcycle/traffic_cone AP 0（预测极少）——PV-RCNN 3-class / CenterPoint 10 类的类别覆盖验证（按 difficulty 分层看，区分「数据稀少」与「模型短板」）
- 复用 v0.2 基建：`detection3d.py` Mmdet3dDetector（模型名路由扩展）、双引擎路由、双口径评测（官方 40-point / 11-point）
- **P2 验收**：KITTI PV-RCNN 全 val 官方口径出表（Car moderate vs 82.0 对比）+ Cyclist 非零（或分层说明）；nuScenes CenterPoint 简化评测出表（vs 17.7 对比）；难类结果如实记录

## Phase 3：BEVFusion 相机-LiDAR 融合 ✅

- **nuScenes（主战场）**：补 sparse-checkout `configs/bevfusion/` + openmmlab 权重（`bevfusion_lidar-cam_voxel0075_second_secfpn_8xb4-160e_nus-3d`）→ 简化评测同口径对比（NDS 76.1 为 zoo 全量口径，仅参考）
- **KITTI（降级路线，评审修正）**：官方无融合权重；**降级选型前置小验证**——P3 开头先跑通一个单目 config（fcos3d/monoflex/pgd，config 已 sparse-checkout）冒烟再定：
  - **默认优先**：单目分支交叉验证（同帧 3D 结果对比表，成本低、现成 config）
  - 可选：相机检测 → 投影 → LiDAR 匹配的后融合原型（自写，成本高）
  - KITTI 融合缺口如实记录
- **红线**：融合输入必须走标定链（nuScenes calibrated_sensor 两级补偿教训 M7）；相机分支推理用 auto2dlabel 2D 基建或 mmdet3d 单目，不自造
- **P3 验收**：BEVFusion nuScenes 简化评测出表（vs pointpillars_nus / centerpoint 对比）；KITTI 降级方案落地一项 + 缺口如实记录

## Phase 4：Web 真 3D 复核可视化（three.js）✅ P4a（P4b 可选未做，如实记录）

- three.min.js 单文件本地化入 `web/static/`（~600KB；**下载源记录**：npm/jsdelivr 一次性下载，**运行时纯本地 CDN 零引用**，不破纯本地红线；库文件入库，权重不入库红线不变）
- **P4a 只读可视化（必做）**：
  - **点云渲染**：KITTI `.bin` / nuScenes pcd → BufferGeometry Points（10 万点级，可选下采样）；**cuboid 网格**（Box3D 六面 + 方向线）；**四视图**：透视 + Top/Side/Front 正交（CVAT 借鉴：正交投影只显选中对象 + 自动聚焦）
  - **交互**：旋转/缩放/选中/改标签/保存回写（Box3D 字段经 to_dict 穿透点纪律，新增 Web 编辑路径不得绕过）
  - 复核队列协议扩展：review 文件已有 pcd_path/calib/3d_annotations 字段设计（v0.1 预留），补齐前端消费
  - **P4a 验收**：Web 打开 KITTI 帧 → 点云 + 3D bbox 四视图可交互、选中/改标签/保存回写 → 导出 label 校验；与 2D Web 复核（:8765）同端口共存
- **P4b 手柄编辑（可选，延后或降级）**：cuboid 六面拖拽手柄 + raycast 吸附（v0.3 最重前端单块，1000+ 行 JS；P4a 闭环交付后评估是否本期做）

## Phase 6：mmdet3d 模型矩阵扩展 + 共享 Token 工程（2026-08-30 追加）✅

> 背景：mmlab 全家桶盘点（2026-08-30）——mmdet3d 1.4.0 已是 3D 主力（detection3d / mono3d(pgd) / bevfusion3d 全基于它）；mmcv/mmengine 纯依赖无直接产品价值（不立项）。扩展方向聚焦**质量档与速度档**，沿已跑通的 `detection3d.py` 四段式母版接入。

### P6a：P3 收尾前置

- mono3d.py（pgd KITTI 单目）/ bevfusion3d.py（nuScenes 融合）代码已落盘但**未验收**——P6 开工前先完成 P3 冒烟出表（KITTI mono 20 帧 + nuScenes 简化评测），补齐测试记录（test-v0.3.md P3 段）
- 验收标准同 P3 原定义：BEVFusion nuScenes 出表（vs pointpillars_nus 17.7 / centerpoint 对比）；KITTI 单目降级方案落地一项

### P6b：模型矩阵扩展（质量/速度档）

| 模型 | 档位 | 依据 |
| --- | --- | --- |
| **TransFusion**（nuScenes） | 融合质量档 | BEVFusion 之外的第二融合系（v1.4.0 现成 config + 权重）；同口径简化评测对比 |
| **FCOS3D / SMOKE**（nuScenes） | 单目质量档 | 单目系扩展（pgd 是 KITTI 侧），覆盖无 LiDAR 域交叉验证 |
| **VoxelNeXt**（nuScenes） | 速度档 | 全稀疏 64ms/帧（技术选型速查已论证），大批次标注提速 |
| 其余（mmtrack / mmcv / mmengine） | 不引入 | mmtrack 官方停止维护、2D 自研 BoT-SORT 已验证更优（决策详 v0.6 Phase 3 盘点）；mmcv/mmengine 纯依赖 |

- 接入形态：`detection3d.py` Mmdet3dDetector 路由扩展（模型名 → config+权重），复用 P2 评测基建（简化评测 + 双口径），零新框架
- **P6b 验收**：每模型 20 帧冒烟 + 简化评测出表（vs 既有数字对比）；速度档报耗时（对照 CenterPoint 基线）

### P6c：共享 Token 工程（LLM Harness，v0.6 Phase 4 收益 3D 共享）

- 3D 与 2D 共用同一 LLMClient（planner3d.parse_dialog 复用 dialog.py 骨架）——v0.6 Phase 4 的 usage 台账 / max_tokens / json mode / 前缀缓存 / Evaluate 降级改造**自动覆盖 3D 侧**，无需单独实现
- 验收：3D chat 调用进同一台账（cost-report 按调用点区分 2D/3D）；planner3d 输出走 json mode 无回归

## Phase 5：LabelAny3D 无 LiDAR 域验证 ✅（评审修正：加前置侦察 + 预算放宽；决策：不接入）

- **前置侦察（半天）**：源码可复现性 / 权重可用性 / 许可证（Objaverse/TRELLIS 依赖合规）→ 侦察不通过直接出调研报告
- **验证（复现预算 2-3 天）**：KITTI 20 帧 val 小规模复现 vs GT 3D IoU
- **达标判据**：moderate 3D AP 显著高于 v0.1 反投影基线（近零）、与单目检测水平（moderate ≤30%）相当或更好 → 达标接入管线第三引擎（无 LiDAR 数据源分支：行车记录仪/网络视频）；不达标 → 调研报告落盘（方法/权重/许可证/预期），不接入
- 分析合成路线：相对深度 + Objaverse 形状先验 / TRELLIS 式重建 + SAM/G-DINO；验证阶段隔离跑，不接主线管线
- **P5 验收**：侦察结论 + 验证报告（20 帧 vs GT 3D IoU 数字）+ 接入/不接入决策落盘
