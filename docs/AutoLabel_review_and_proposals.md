# AutoLabel v0.1a — 外部评审总结与待评估提案

> **本文档用途**：由外部评审者阅读 `AutoLabel_plan.md`（490 行，v0.1a 已交付）后产出。
> **请 Claude Code 判断**：下列 4 项提案是否值得做、优先级是否合理、工作量估算是否准确、有无更优替代方案。
> **决策背景**：作者为 2025 届毕业生，正在面试某德系 Tier 1 的「感知融合算法工程师」岗位（一面已过部门经理，二面预计由技术 Lead 主持）。本项目是面试官建议的「用 AI Agent 从 0 到 1 做个人工程项目」的产物，**同时承担工程价值与面试叙事价值双重目标**。

## 一、项目现状（评审者理解）

**已交付 v0.1a**：

- Agent Loop（自建 ~200 行，参考 Anthropic tool-use 协议）
- 3 个检测引擎 × 47 个模型（Grounding DINO / Ultralytics YOLO / PyTorch Vision）
- 单一暴露 Tool：`detect_objects`
- 导出：COCO JSON / YOLO txt / Pascal VOC XML
- CLI（Typer + Rich）、结构化 JSON 日志、可视化 PNG
- LLM：DeepSeek（OpenAI 兼容），2 轮迭代完成

**技术栈**：Python 3.10+ 单语言

| 岗位相关性 | 6/10 | 目前是通用 CV 工具，与「感知融合」无直接关联 |

### 核心诊断

**问题不是「项目不够大」，而是「核心价值主张未被证明」。**

计划书自述的实现细节暴露了一个矛盾：

> 「LLM 只负责翻译 prompt + 调用检测 + 简要总结」
> 「2 轮迭代完成，Token 消耗降至最低」
> 「防重复调用：第二次调用 detect 时直接 skip」
> 「max_iterations 设为 3」（实际只跑 2 轮）

**推论**：当前 LLM 层的实际功能约等于「中英翻译器 + 一次函数调用」。所有既有优化都在**削减 Agent 自主性**，即项目正朝确定性 pipeline 退化。这说明在单一检测任务场景下，Agent 的自由度尚未产生可观测价值。

**这不构成放弃 Agentic 路线的理由，但构成必须建立对照组的理由。**

## 三、待评估提案（按建议 ROI 排序）

### 📌 提案 1：`--no-llm` baseline 模式 + 对照实验

**估时**：0.5 天

**动机**：直接回答 Q1 与 Q2。同时兼作 LLM API 的降级路径（当前 DeepSeek 为单点外部依赖，风险章节声称「可换本地 Qwen」但未实现）。

**范围**：

1. 新增 CLI flag `--no-llm`：绕过 Agent Loop，使用静态关键词映射表（中→英）+ 用户指定模型，直接调用 `DetectionTool`
2. 在 COCO val 上抽 50–100 张图，跑两条路径产出对比表：

   | 路径 | 召回 | 类别覆盖率 | 平均延迟 | Token 成本 |
   | --- | --- | --- | --- | --- |
   | LLM Agent | ? | ? | ? | ? |
   | 关键词映射 baseline | ? | ? | ? | 0 |

3. 将结论写入计划书新增章节

**验收标准**：

- `--no-llm` 路径与 LLM 路径产出格式完全一致（可直接 diff）
- 对比表有真实数字，样本量 ≥ 50 张
- 计划书中明确记录结论（无论结论方向）

**关键说明（供 Claude Code 判断）**：
**即使实验结论是「LLM 层无优势」，本提案依然成功**。因为它使作者能够表述：

> "我做了对照实验，发现在单一检测任务上 LLM 层的边际价值接近零。其价值需在多任务编排（检测+分割+分类组合）和歧义指令（如'检测所有红色车辆'）场景下才体现。因此我把 v0.1b 重点从『加模型』改为『加编排复杂度』。"

即：**用工程方法证伪自身初始假设并据此调整路线**，其叙事价值高于任何功能列表。

---

### 📌 提案 2：多模型框级融合（WBF / multi-model NMS）

**估时**：1–2 天

**动机**：

1. **技术动机**：项目已有 3 个引擎，且计划书实测记录显示引擎间检出差异巨大（同一张图 person 类：`fasterrcnn_resnet50_fpn_v2` 检出 16 个 vs `yolov8n` 检出 6 个）。这是现成的 ensemble 机会，当前完全未利用。
2. **叙事动机（更重要）**：**多模型框融合 ≈ 多传感器目标级融合的简化同构问题**。二者都是「同一场景下多个异构源产生冲突观测 → 关联 → 冲突消解 → 融合输出」。IoU 对应马氏距离，置信度加权对应协方差加权。这是**唯一能让本项目与目标岗位直接对口的改动**。

**范围**：

1. 新增 `FusionTool` 或 `fuse_detections()`：接受多个引擎的 `List[Bbox]`
2. 实现 WBF（Weighted Box Fusion）：IoU 聚类 → 置信度加权平均坐标 → 重打分
3. 对比实验：单模型 vs 2 模型融合 vs 3 模型融合的召回 / 误检率
4. CLI 支持 `-d model_a -d model_b`（多次传参）触发融合

**验收标准**：

- 融合后召回相对最佳单模型有可测量提升（或记录为何未提升）
- 有一份 late fusion 的设计说明，明确 IoU 阈值、加权策略、冲突消解规则

---

### 📌 提案 3：置信度分流 + 困难样本导出（兑现 HITL 叙事）

**估时**：0.5 天

**动机**：计划书第 5 节（HITL 与主动学习闭环：τ_high/τ_low 分流、困难样本池、主动学习采样）是**声明的核心差异化来源，但状态为未实现（📋）**。当前存在「文档承诺 vs 代码交付」的落差。该功能实现成本极低但叙事等级提升明显（从「预标工具」升为「带 HITL 分流的标注系统」）。

**范围**：

1. 按置信度三档分流（阈值可配置）：
   - `conf >= τ_high`（默认 0.7）→ 直接采纳，进正式导出
   - `τ_low <= conf < τ_high`（默认 0.3–0.7）→ 写入 `review_queue.json`
   - `conf < τ_low` → 写入 `hard_samples.json`
2. 分流统计写入现有 JSON 日志的 `steps` 字段
3. 计划书第 5 节状态从 📋 更新为部分完成

**验收标准**：三个输出文件正确生成，计数之和等于总检出数

---

### 📌 提案 4：导出格式 round-trip 测试

**估时**：0.5 小时

**动机**：三种导出格式坐标约定互不相同，是 off-by-one 与归一化错误的高发区：

- COCO：`[x, y, w, h]` 绝对像素
- YOLO：`[cx, cy, w, h]` **归一化**
- VOC：`[xmin, ymin, xmax, ymax]` 绝对像素

而项目 `tests/` 目录当前为空。这是全部提案中**性价比最高**的一项（外部评审者若 clone 仓库看到空 tests 会直接扣分）。

**范围**：3 个 pytest，每种格式一个：构造已知 Bbox → 导出 → 重新解析 → 断言误差 < 1e-6

**验收标准**：`pytest` 通过，覆盖三种格式

## 四、建议暂缓项

### ⛔ SAM2 集成（原 v0.1b 计划）

**建议从 v0.1b 后移。**

**理由**：SAM2 集成本质是「多一个模型 + 多一种输出类型」。它：

- 不改变任何核心论述
- 不回答 Q1 / Q2 / Q3 中的任何一个
- 不提升与目标岗位的相关性

在时间受限（二面可能在 1–2 周内）的前提下，其 ROI 低于上述 4 项。**待提案 1–4 完成后再做。**

| 5 | **Schema 扩展性不足** — `Bbox / Mask / Annotation` 撑不到 v0.3。Pose 需 keypoints、OBB 需角度、tracking 需跨帧 `track_id` | 建议现在就重构为 `geometry: Union[Bbox, Mask, Keypoints, OBB] + attributes: dict`，否则 v0.2 会破坏性重构 |
| 6 | **「47 个模型」是虚荣指标** — 实为 3 个 wrapper + 权重名列表。且计划书第 11 节「模型选型速查」把选型决策负担推回给用户，**与「Agentic / AI 为主」的主张直接矛盾** | 真正 Agentic 的做法：Agent 根据图像特征（分辨率、目标密度、首轮检出数）自动选模型和阈值。这可作为提案 1 实验结论支持「加编排复杂度」路线时的 v0.1c 候选功能 |

## 六、请 Claude Code 评判的具体问题

1. **提案 1（baseline 对照）的前提推论是否成立？** 即：从计划书自述的「LLM 仅翻译+调用+总结」「防重复调用」「2 轮完成」，是否足以推断当前 Agent 层价值接近零？还是评审者误读了实现？

2. **提案 2（WBF 融合）的类比是否过度？** 「多模型框融合 ≈ 多传感器目标级融合」这个类比在技术上是否站得住？会不会在真正的感知融合工程师面前显得牵强（例如：缺少时序、缺少状态估计、缺少异构传感器的坐标系与不确定性建模）？如果牵强，是否有更贴切的改动方向？

3. **优先级排序是否合理？** 特别是：把 SAM2 后移、把「无量化数据」列为最大缺口，是否符合工程判断？还是过度偏向了面试叙事而牺牲了产品演进？

4. **工作量估算是否现实？** 4 项合计约 2.5–3 天（含实验跑数），对一个单人 Python 项目是否可行？

5. **是否存在遗漏的更高 ROI 改动？** 尤其是能同时提升工程价值与岗位相关性的方向。

6. **问题 1（Evaluate 节点为空）是否应升级为正式提案？** 评审者将其排除在提案外的理由是估时不确定，但它可能是「让 Agent Loop 真正成为 loop」的关键——这一点是否被低估了？
