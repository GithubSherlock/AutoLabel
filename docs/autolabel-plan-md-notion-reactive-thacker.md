# AutoLabel v0.1a 评审回应 & 修订计划

## 一、对评审结论的确认

### 完全同意

| 评审判断 | 确认理由 |
| --- | --- |
| **LLM 当前价值接近零** — 在单一检测任务上约等于"中英翻译器 + 一次函数调用" | 正确。2 轮迭代、防重复调用、max_iterations=3 全都证明 Agent Loop 实际退化成了确定性 pipeline。这不是 bug——这是当前任务复杂度不匹配 Agent 能力的必然结果 |
| **最大缺口是「零量化数据」** — 无法回答"LLM 层去掉行不行"和"比裸模型好多少" | 这是面试必杀问题，必须优先解决 |
| **提案 1（baseline 对照）是最高 ROI 的第一步** | 无论结论方向（LLM 有价值 vs LLM 无价值），都能产生可辩护的工程叙事 |
| **HITL 分流（提案 3）实现成本极低但叙事提升大** | 计划书第 5 节声明的核心差异化，代码里没兑现 |
| **导出 round-trip 测试（提案 4）是性价比最高的改动** | 空 tests/ 目录在技术面试中是致命减分项 |
| **SAM2 应后移** — 加一个模型不改变任何核心论述 | 不在二面时间窗内产生足够 ROI |
| **默认模型应体现产品主张** — 实测最佳是 FRCNN_V2，默认却是 GDINO-tiny | 5 分钟改一行代码 |
| **target user 未定义** | 文档应补 |

### 需要修正的评审判断

| 评审主张 | 修正 |
| --- | --- |
| "Agent Loop 的 Evaluate 节点为空，架构图画了循环但实现不循环" | **部分同意**。当前 Evaluate 确实为空——LLM 只摘要不触发重试。但 `max_iterations=3` 跑 2 轮不是因为"循环不工作",而是因为**当前任务只需 detect→summarize 两步**。真正需要 Evaluate 触发重试的场景是：要 3 类只出 2 类→降阈值重试、出 0 框→换模型重试——这些在提案 3 的 HITL 分流中自然会用到 |
| "47 个模型是虚荣指标" | **不同意**。模型工厂 + Protocol 接口 + 自动引擎识别是工程能力证明，不是虚荣指标。但如果用户需要自己从 47 个中选，确实违背了 Agentic 主张。改进方向：v0.1c 时 Agent 根据首轮结果自动推荐（非选举） |
| "WBF ≈ 感知融合"的类比 | **同意需谨慎**。对感知融合岗的技术 Lead，如果只说"IoU 聚类 ≈ 马氏距离关联"会被追打到露出破绽（缺时序、缺状态估计、缺传感器模型）。正确的叙事方式：**"这是一个感知融合思想的轻量应用——不是声称等同，而是展示我对融合范式的理解"** |

## 三、关键设计决策

### 1. `--no-llm` 的实现方式

```python
# 不引入新的 Tool 或改变架构
# 在 cli.py run() 中增加分支：
if no_llm:
    from auto2dlabel.models.detection import create_detection_model
    # 中→英关键词映射表（与 orchestrator 中的 _cn_map 共用）
    # 直接调用 model.detect()，跳过 Agent Loop
    # 输出格式与 LLM 路径完全一致（Annotation → export → log）
```

### 2. 模型默认值

```python
# auto2dlabel/configs/.env
DETECTION_MODEL = fasterrcnn_resnet50_fpn_v2  # 改为实测最优
```

### 3. 提交策略

每个 patch/version 一个 git commit，确保 `git log` 清晰展示项目演进（面试时 `git log --oneline` 就是最好的进展证明）。

## 四、对 Notion AI 6 个问题的直接回答

**Q1: 提案 1 前提推论是否成立？**
→ 成立。从代码实现推断 LLM 当前价值接近零是正确的。但这不是架构缺陷——是当前 v0.1a 只有检测这一个 Tool，编排复杂度天然为 1。价值在多 Tool（检测+分割+分类）组合时才会显现。对照实验的目标正是量化这个边界。

**Q2: WBF 融合类比是否过度？**
→ 有牵强风险。对感知融合岗的面试官说"IoU ≈ 马氏距离"会被追问时序、状态估计、传感器模型等问题。建议叙事方式改为："这是融合思想的轻量实践——理解关联→冲突消解→融合输出这一范式。严格等价需要引入时序和不确定性建模，那是后续演进方向。"做好被追问的准备比不说强。

**Q3: 优先级排序是否合理？**
→ 总体上合理。但 SAM2 后移是正确判断，不是过度偏向面试叙事——在当前二面时间窗内，证明工程能力和思维完整性比功能数量重要得多。
建议微调：文档补丁（P1-P3）的估时过于乐观，实际约 0.5 小时；作为 v0.1a-patch 的一部分先提交，为后续提案 1-4 开路。

**Q4: 工作量估算是否现实？**
→ 偏乐观。2.5-3 天是理想情况（不限打扰、环境稳定）。加上踩坑和调试，建议估算为 3-4 天。COCO val 50 张图的对照实验可能因模型下载/推理耗时而膨胀。

**Q5: 是否存在遗漏的更高 ROI 改动？**
→ 有一个：**给 Agent Loop 加最简 Evaluate 判据**（类别覆盖检查：要 3 类只出 2 类→降阈值/换模型重试）。实现成本低（~50 行代码）且能直接回答"你的 Agent 真的有循环决策能力吗"这种面试问题。建议纳入 v0.1c。

**Q6: Evaluate 节点是否应升级为正式提案？**
→ 是的，评估节点的判据确实是"让 Loop 真正成为 loop"的关键。建议纳入 v0.1c，与 HITL 分流组合实现：分流逻辑覆盖 LLM 初判，LLM 反思覆盖低置信度区间的重试逻辑。这构成了 mini NLP 评估闭环——在面试中是有价值的叙事物。

## 六、不变的核心原则

> **无论实验结果如何——即使证明 LLM 对单一检测无价值——都不等于 Agentic 路线失败。** v0.1a 已经证明架构的扩展性（3 引擎 × 47 模型一键切换）。当 v0.1b/c 引入多任务编排（检测→分类验证→分割细化）和歧义指令（"标注所有红色的车"）时，Agent 的决策价值才会被证明。0.1a 的对照实验是**划清价值边界**，而非推翻路线。
